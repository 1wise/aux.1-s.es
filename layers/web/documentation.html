# AUX 8.0.1-beta.5 — contraseñas y raíz visible de Bastion

Timestamp: 2026-11-23 | Version: 8.0.1-beta.5
Author & Credits: https://www.alawise.es/1-s

La beta.4 permitía el aviso nativo de SSH, pero no tenía un campo para guardar su contraseña. Además, el error FTP agrupaba login, TLS y directorios en un mensaje único. La beta.5 corrige ambos puntos y permite revisar el directorio FTP sin adivinar equivalencias con SSH.

Desde ./aux checkstatus --interactive, B abre Bastion con estas opciones:

1. Contraseña SSH / rsync: entrada oculta, guardada como ssh_password. Selecciona mirror.ssh_auth=password.
2. Contraseña FTP / FTPS: entrada oculta e independiente, guardada como ftp_password.
3. Editar conexión: host, usuario, puerto y raíz propios de SSH o FTP. SSH incluye autenticación, identidad y known_hosts opcionales.
4. Probar SSH / rsync: confirma autenticación y un comando de lectura. No comprueba todavía todos los permisos de rsync ni arranque.
5. Probar FTP / FTPS: muestra PWD tras login, carpetas visibles y si la raíz configurada es accesible.
6. Explorar FTP: navegar por las carpetas que muestra la cuenta, elegir la raíz pública y revisar sus equivalencias antes de APLICAR.

Una ruta como /home/cuenta/bastion puede existir en SSH y no ser visible en FTP. El servidor FTP puede mostrar / como inicio y bastion como subcarpeta. Este es solo un ejemplo: la selección se basa en el listado real. El explorador corrige ftp_root y la equivalencia ftp_path del inventario; no cambia la raíz SSH. Al terminar, activar el inventario con la conexión revisada y ejecutar C.

Comandos equivalentes, desde las fuentes de la suite:

    ./aux-config secret ssh_password
    ./aux-config secret ftp_password
    ./aux-config test-connection rsync
    ./aux-config test-connection ftp

Usar --config y --secrets antes del subcomando si se utilizan rutas personalizadas. El almacén privado tiene modo 0600 y su carpeta 0700, fuera del código y la web. Se utiliza el almacén del usuario que ejecuta AUX: una ejecución como root no lee automáticamente el de otra cuenta. No poner las contraseñas en fast-boot.json, config.json, el catálogo, una URL ni los argumentos del comando.

SSH usa SSH_ASKPASS_REQUIRE=force cuando hay contraseña guardada. Un helper temporal lee una tubería privada 0600 dentro de una carpeta 0700. La contraseña permanece en memoria y en la tubería; no se escribe en el helper, en un archivo de texto temporal, en argumentos o en variables de entorno. La carpeta y la tubería se eliminan al finalizar. Checkstatus, deploy y las transferencias/verificaciones rsync utilizan el mismo mecanismo. Sin contraseña guardada, el modo password puede solicitar entrada oculta en una terminal. El modo key conserva claves/agente y no utiliza ssh_password.

StrictHostKeyChecking=yes permanece activo. Un fallo de known_hosts se comunica antes de tratarlo como un problema de contraseña. Verificar la huella desde la misma cuenta que ejecuta AUX; no se aceptan huellas nuevas automáticamente. Referencia: [OpenSSH ssh](https://man.openbsd.org/ssh), SSH_ASKPASS_REQUIRE.

FTP informa la fase: conexión, TLS, login, protección de datos, PWD, directorio o listado/datos. Un directorio rechazado incluye la raíz solicitada y el PWD observado después del login. Los errores de autenticación eliminan contraseñas conocidas del texto. La conexión FTPS valida el certificado y mantiene protegida la conexión de datos. La conexión FTP usa siempre ftp_root aunque el transporte principal del mirror sea rsync.

Las pruebas de conexión y exploración no suben ni descargan imágenes. Listados y tamaños no acreditan un hash remoto ni llegada al login. Las credenciales reales de Bastion no se han utilizado durante la validación: se comprueban autenticación OpenSSH y FTP/FTPS en servidores de prueba locales, con contraseña, raíz aislada y certificado de prueba de confianza explícita.

Validación: dieciocho pruebas nuevas; 549 casos Python, 530 ejecutados correctamente y 19 omitidos. SSH y FTP/FTPS se prueban contra servidores locales reales. El acceso concreto al alojamiento y sus permisos de rsync quedan pendientes de repetir con las credenciales de la instalación.

# AUX 8.0.1-beta.4 — inventario Bastion y conexiones existentes

Timestamp: 2026-11-23 | Version: 8.0.1-beta.4
Author & Credits: https://www.alawise.es/1-s

Guardar la conexión FTP no activaba el inventario de checkstatus. Si checkstatus.bastion.enabled era false, la beta.3 terminaba sin intentar Bastion y sin explicar ese motivo. La beta.4 muestra el estado remoto, la configuración utilizada, los intentos, la alternativa elegida y el número de archivos observados.

En el tablero de 24 casillas, B abre Bastion. «Activar con el FTP/FTPS ya configurado» reutiliza host, usuario, puerto, ftp_root y la contraseña del almacén privado; muestra la raíz y su URL pública antes de APLICAR. No exige volver a introducir la contraseña. Después, C ejecuta checkstatus incluyendo Bastion. El mismo acceso está en AUX Config → Inventario Bastion.

Para una comprobación puntual desde consola, con el FTP configurado:

    ./aux checkstatus --bastion ftps

El parámetro incluye Bastion en esa ejecución, utilizando ftp_root y la URL pública de targets.bastion.base_url o download_url. No modifica la configuración guardada. El status conserva la huella de la configuración original y se puede utilizar después con generate. Añadir --dry-run muestra el alcance sin conexiones ni escrituras. --show solo muestra el informe guardado.

SSH admite contraseña sin clave privada ni certificado de cliente. mirror.ssh_auth acepta auto, key o password. Auto permite el diálogo de contraseña de OpenSSH cuando hay una terminal y utiliza modo por lotes cuando no la hay. Password necesita terminal; key mantiene la autenticación por claves/agente. La contraseña SSH no se guarda en el catálogo, argumentos ni variables de entorno, y no se reutiliza la contraseña FTP como contraseña SSH.

Se conserva StrictHostKeyChecking=yes. La identidad del servidor debe estar validada en known_hosts. No se desactiva esa comprobación para facilitar el acceso. Referencia técnica: [OpenSSH ssh_config](https://man.openbsd.org/ssh_config), BatchMode y NumberOfPasswordPrompts.

Si falla rsync y checkstatus.bastion.fallback_ftp está activado, el inventario usa la conexión FTP/FTPS ya configurada. Las raíces pueden ser distintas: SSH puede mostrar /home/cuenta/www y FTP /site. Cada directorio admite ftp_path para declarar la equivalencia. Si no se indica, solo se deriva una ruta cuando path pertenece a mirror.remote_root y existe ftp_root. No se utiliza una raíz SSH desconocida como raíz FTP.

El transporte alternativo respeta ftp_tls. FTPS sigue validando el certificado del servidor; un fallo no se convierte automáticamente en FTP sin TLS. El inventario solo lista nombres y tamaños: no sube ni descarga imágenes ni acredita hashes remotos o arranque hasta login. Si una conexión falla, las observaciones quedan desconocidas, conservando el antecedente de la última comprobación correcta; no se declaran ausentes por un error de acceso.

La activación sigue siendo explícita: desactivar Bastion se respeta y produce un aviso visible. Los perfiles sin conexión configurada no intentan acceder a servidores de ejemplo. La raíz y la URL pública deben corresponder al mismo contenido para generar enlaces correctos.

Validación: 21 pruebas nuevas; 531 casos Python, 512 ejecutados correctamente y 19 omitidos. Se validan las opciones de OpenSSH sin conectar. Las pruebas usan conexiones simuladas para autenticación y alternativa de inventario; falta repetir la conexión real desde el equipo con sus credenciales.

# AUX 8.0.1-beta.3 — tamaños y continuidad de deploy

Timestamp: 2026-11-23 | Version: 8.0.1-beta.3  
Author & Credits: https://www.alawise.es/1-s

Deploy completa los metadatos pendientes antes de calcular la capacidad. La beta.2 detenía todo el lote si el catálogo local carecía de un tamaño, aunque la imagen ya estuviese descargada y el catálogo publicado lo tuviera resuelto.

Si existe un SHA-256 esperado, se verifica el archivo completo de caché y se obtiene su tamaño real. Se admiten la ruta de artefactos y la antigua caché plana. Esta observación local no se presenta como un checksum oficial nuevo. Un archivo parcial o sin checksum esperado no sirve para autenticar la imagen.

Cuando faltan metadatos y C permite resolver y rastrear, se consulta el origen mediante las reglas configuradas. Se conservan las políticas, prioridades y sectores manuales. Una versión ya autenticada no se sustituye por la más reciente durante deploy: ese cambio requiere catalog refresh y download expresos. Los metadatos completos no se refrescan por estar en una URL mutable. Deploy no descarga las imágenes.

El catálogo actualizado y su SHA-256 se guardan antes del cálculo. Los recursos sin tamaño o checksum comprobable quedan pendientes y aparecen en el informe; no se presupuestan como cero ni se despliegan. El resto continúa dentro de los límites configurados. Los fallos por recurso o destino tampoco interrumpen los demás; los conflictos globales de presupuesto mantienen el bloqueo.

El informe deploy-report.json se guarda junto al status_file configurado, con el ID, destino, etapa, resultado y error. La salida conserva progreso por recurso y un resumen final. Cualquier fallo devuelve código 1; conviene revisar el informe antes de ejecutar checkstatus y generate. Un deploy correcto no acredita arranque hasta login.

Tras actualizar las fuentes a beta.3, repetir la selección habitual de deploy. Si falta la imagen, ejecutar antes download. El plan sin --apply y cualquier --dry-run siguen sin consultas de red ni escritura de catálogo.

| ID estable | Recurso |
| --- | --- |
| other-tool-x86_64-nixos-minimal-26 | NixOS Minimal 26.05, x86_64 |
| other-tool-x86_64-agama-installer | Agama Installer, openSUSE Leap 16.0, x86_64 |

No es necesario cambiar casillas de disponibilidad o estado para resolver tamaños. A/S siguen siendo observaciones; las políticas C/D/E y prioridades P se conservan.

Validación: 510 casos Python, 491 ejecutados correctamente y 19 omitidos; trece pruebas nuevas de recuperación, conservación de versiones, los dos resolutores afectados, copia local y continuidad del lote. No se han desplegado las distribuciones en los servidores del proyecto.

Red Robin: precauciones y herramientas sensibles

# Blue Hibou y Red Robin — despliegue y precauciones

Timestamp: 2026-11-27 | Version: 8.0.1-beta.8  
Author & Credits: https://www.alawise.es/1-s

Blue Hibou identifica las notas y procedimientos de despliegue rápido. Red Robin identifica avisos y precauciones; la etiqueta RED TEAM señala herramientas u operaciones que requieren especial atención. La etiqueta describe su capacidad e impacto operativo, no acusa al programa de ser malicioso ni acredita una auditoría de seguridad.

| Área | Riesgo concreto | Medida operativa |
| --- | --- | --- |
| aux-assist, SSH, Cockpit y gateways | Abrir terminales o administración con privilegios y exponer servicios a la red. | Selección opcional; comprobar identidad, destino, puertos, firewall/VPN y consentimiento; revisar el cierre. |
| Instalación en sistema actual | Cambiar paquetes, cuentas, servicios o configuración del equipo real. | Revisar hostname y plan antes de APLICAR; contar con recuperación y acceso local. |
| RAM y tmpfs | Agotar memoria que usan el sistema y otros procesos, aunque la cuota nominal parezca suficiente. | Leer MemAvailable; conservar reserva; reducir selección y concurrencia. |
| Caché, extracción y réplicas | Consumir SSD, inodos, ancho de banda e I/O; un árbol extraído puede crecer más que su ISO. | Separar imágenes/deploys, comprobar espacio real y dejar margen. |
| Escrituras y arranque USB | Escribir en un destino equivocado o modificar datos y cargadores. | Identificar ruta y dispositivo; verificar sumas y copias antes de grabar. |
| Tareas permanentes y cargas intensivas | Mantener CPU, RAM, I/O o red ocupados durante tiempo indefinido. | Definir duración, límites, supervisión y parada antes de habilitar un servicio o timer. |

## Herramientas remotas

AUX Assist y el rol de administración que contiene Cockpit quedan fuera de la selección inicial. Se pueden elegir expresamente. La base conserva el cliente SSH y deja de incluir el servidor SSH; la tarea Debian ssh-server también queda sin preseleccionar. Instalar un paquete no equivale a autorizar una intervención. Las unidades propias de asistencia siguen siendo de inicio manual; los paquetes de la distribución pueden iniciar servicios o sockets según sus políticas. Revisar el estado y los puertos reales después de instalar.

La acción local de Cockpit muestra la advertencia y exige escribir INICIAR COCKPIT antes de iniciar cockpit.socket. La web prepara la selección y abre una URL indicada; no instala ni inicia servicios en los servidores por sí misma. El cliente de asistencia mantiene sus controles de consentimiento, identidad y cierre. Antes de permitir root, verificar el contacto y la huella del técnico.

## Cuotas, disponibilidad y carga

Los presets 10 GiB RAM / 75 GiB SSD por preset son propuestas para una máquina de referencia. No son un requisito para usar AUX ni una reserva física. El tablero mantiene las previsiones y los límites configurados; una máquina compartida necesita valores menores y margen para su trabajo habitual.

Antes de una nueva descarga de tamaño conocido se contrasta el espacio pendiente con el sistema de archivos de caché, dejando 1 GiB de reserva. Antes de desplegar se comprueba el destino local: en RAM se usa MemAvailable y se conserva al menos 512 MiB o el 20 % de MemTotal, el mayor; en disco, 1 GiB. Las comprobaciones no sustituyen la medición del árbol extraído ni un límite de CPU, I/O o memoria por proceso. No pueden reservar capacidad frente a otros procesos concurrentes.

No se habilitan nuevas cargas de estrés ni tareas permanentes mediante el tablero. Cualquier futura herramienta de carga debe incluir alcance, duración, límites efectivos y una parada verificable. Un timer, socket o daemon necesita revisión propia, además de la cuota del catálogo.

## Cierre de la intervención

Cerrar la sesión autorizada y comprobar que los accesos temporales han terminado. Revisar servicios y sockets que se hayan iniciado, procesos, montajes, cuentas o claves temporales y tareas programadas. Conservar el informe y las evidencias necesarias. No detener servicios ajenos a la intervención sin conocer su función.

Los avisos aparecen junto a las herramientas, en los planes y en la documentación; los emblemas no sustituyen el texto, para que las precauciones sigan siendo legibles en Links, consola y lectores de pantalla.

# Tablero común de 24 casillas

Timestamp: 2026-11-27 | Version: 8.0.1-beta.8  
Author & Credits: https://www.alawise.es/1-s

Estado y selector de catálogo comparten una tabla: una fila por recurso, 24 casillas en orden 23–0 y una ficha Info. La cabecera explica P A S C D E una sola vez. Buscar y filtrar permite trabajar con catálogos amplios; la fila no se reparte en tarjetas. En pantallas estrechas la tabla se desplaza horizontalmente. Una raya significa observación desconocida.

P y CDE se editan. A y S solo reflejan observaciones de checkstatus; marcar una política no declara presencia, integridad ni arranque hasta login. Los menús remotos conservan sus restricciones de destino. La ficha desglosa procedencia, versión, arquitectura, tamaño, checksum, observaciones y avisos Red Robin.

En web, elegir recursos y ajustar casillas. Las dos vistas conservan selección y política durante la misma sesión, vinculadas al catálogo y artefacto actuales. Descargar la selección como catalog.json y revisar los comandos de la fase elegida en el equipo configurado. También se puede exportar el catálogo completo e importar una instantánea reciente de checkstatus del mismo artefacto. La web no ejecuta comandos locales ni abre administración remota por seleccionar un recurso.

| Fase | Contrato |
| --- | --- |
| Checkstatus | Observar inventario y evidencias; actualizar A/S y guardar status.json. |
| Download | Adquirir lo indicado por D, resolver según C, verificar y presentar errores del lote. |
| Deploy | Usar fuentes disponibles y los destinos E; mostrar previsión y precauciones de memoria/escrituras. |
| Generate | Publicar desde un checkstatus vigente para el catálogo y la configuración actuales. |

Después de download o deploy, repetir checkstatus antes de generate. Los cuatro pasos permanecen independientes.

En consola: `./aux catalog board` o `./aux checkstatus --interactive`. Los menús de download/deploy/generate también dan acceso al tablero. Flechas: fila y casilla; Espacio: cambiar; /: buscar; I o Enter: ficha; F1: ayuda. S revisa y guarda P/CDE con APLICAR. C/D/P/G abren las fases; las que aplican cambios conservan su plan y EJECUTAR. Esc vuelve y descarta ediciones sin guardar. El filtro cambia la vista, no el alcance de las fases: estas usan la política del catálogo completo.

La consola de 80 columnas conserva los 24 estados en seis grupos de cuatro caracteres: x activo, punto inactivo y ? desconocido. Se mantienen alternativas de texto sin pantalla completa. RAM/SSD/Bastion y el exceso previsto permanecen visibles. Los avisos Red Robin explican que las cuotas no reservan recursos ni limitan por sí solas cargas permanentes.

# AUX 8.0.1-beta.6 — cuatro entregas junto al Git

Timestamp: 2026-11-27 | Version: 8.0.1-beta.8  
Author & Credits: https://www.alawise.es/1-s

La versión pasa a 8.0.1-beta.6 al cerrar el uso de los 24 bits. PASCDE conserva sus posiciones y contratos: los cuatro bits P son usuario, tendencia del sector, obligatorio y sugerido por IA para el sector. No hay una migración adicional de bits ni se cambian las decisiones del catálogo.

La matrioshka reúne cuatro entregas hermanas en la raíz del repositorio, al mismo nivel que .git y suite/:

| Archivo | Contenido |
| --- | --- |
| aux-suite-8.0.1-beta.6.zip | Suite completa de fuentes con ambos módulos. |
| aux-pxe-8.0.1-beta.6.zip | Catálogo, Netboot, web y herramientas AUX/PXE. |
| tec-cli-8.0.1-beta.6.zip | Comunidad, cuentas y asistencia TEC/CLI. |
| aux-minimal-ipxe-8.0.1-beta.6.img | Imagen básica USB iPXE, ya sin comprimir. |

Cada entrega tiene su .sha256. RELEASE.json identifica las cuatro, sus tamaños y hashes. La imagen USB conserva el bootstrap existente BIOS/UEFI x86_64; no acredita una nueva Rescue Linux ni una prueba hasta login.

Las fuentes viven en suite/. Los cuatro paquetes se generan fuera de ese árbol para evitar que el paquete completo se incluya recursivamente a sí mismo. El límite de 24.000.000 bytes corresponde al árbol fuente de la suite; las entregas repetidas y el envoltorio se contabilizan aparte.

Desde suite/, preparar las cuatro entregas en la raíz del Git:

    python3 package-release.py --output ..

Conservar una entrega publicada inmutable; usar un destino nuevo para una reconstrucción de revisión. Crear el envoltorio exterior:

    python3 package-matrioshka.py --source-zip ../aux-suite-8.0.1-beta.6.zip --output ../release-artifacts/aux-matrioshka-8.0.1-beta.6.zip

El ZIP exterior contiene las cuatro entregas en su raíz, sus hashes, el desplegador y la web como capa auxiliar. Los metadatos .git no se incluyen en el ZIP. El repositorio Git real conserva su historial y contiene las cuatro entregas.

Después de extraer la matrioshka, revisar el plan:

    python3 DEPLOY.py --web-root ./web-para-subir --sources-root ./repositorio-aux

Aplicar después de revisar:

    python3 DEPLOY.py --web-root ./web-para-subir --sources-root ./repositorio-aux --apply

La web recibe las cuatro descargas. El directorio de trabajo recibe suite/ y, a su lado, las mismas cuatro entregas. Se eligen destinos nuevos; todos los hashes, ZIP y rutas se validan antes de crearlos. El desplegador acepta también las matrioshkas antiguas de tres capas sin cambiar su extracción anterior.

La imagen .img puede usarse con la herramienta habitual de grabación USB. DEPLOY.py solo prepara archivos y no escribe dispositivos. Para Bastion sin Python, preparar la web localmente y subir su contenido por FTPS.

Se conserva Kernel Modeler. Las aportaciones de AP continúan en revisión independiente y no sustituyen el catálogo ni sus resoluciones comprobadas.

El límite de 24 MB corresponde a la suite completa. Réplicas, secciones e imagen básica se contabilizan aparte. La capa web reutiliza los recursos idénticos de las cuatro entregas y los restaura automáticamente al desplegar; los paquetes de producto permanecen completos. Se validan esas referencias antes de escribir. El límite del alojamiento por archivo es independiente del presupuesto del proyecto.

# Kernel Modeler — banco de trabajo de núcleos

## Secuencia de trabajo

1. Definir arquitectura, hardware, controladores y firmware necesarios, objetivo de arranque —disco, ISO o iPXE— y modelo de amenazas.
2. Elegir una versión exacta de Linux y verificar su procedencia. Kernel.org firma el tar sin comprimir: una firma de `.tar` no se verifica directamente contra `.tar.xz`. Conservar URL, checksum, firma, firmante y fecha.
3. Conservar la configuración inicial y usar Kconfig de esa misma versión para resolver sus dependencias. Revisar los símbolos nuevos y el diff; no asumir que una configuración antigua equivale a una nueva.
4. Revisar reducción de superficie, protecciones de memoria, módulos, depuración e interfaces disponibles. El conjunto soportado depende de arquitectura, compilador y versión. La guía de autoprotección del kernel es una referencia, no una certificación automática.
5. Compilar en un directorio separado y conservar versión del compilador, `.config`, logs y hashes. Preparar módulos de la misma versión, firmware e initramfs compatibles.
6. Revisar firma de módulos y cadena de arranque antes de aplicar una política de rechazo. Preparar claves en un espacio privado; su generación o enrolamiento no se ejecutan desde este preset.
7. Probar el conjunto en VM y en el hardware previsto, guardar evidencias y registrar la prueba real en checkstatus. Preparar una ISO o disponer de paquetes no acredita llegada al login.

| A | 19–16 | RAM `1`, SSD `2`, origen `4`, Bastion `8`; disponibilidad observada. |
| S | 15–12 | Fuente `1`, desplegada `2`, receta `4`, comprobada hasta login `8`. |
| C | 11–8 | Nivel en bits 9–8; candidato PXE `4`, resolver `8` dentro del dígito. |
| D | 7–4 | Descargar `1`, actualizar `2`, preservar `4`, archivar `8`. |
| E | 3–0 | RAM `1`, SSD `2`, origen `4`, Bastion `8`; ubicaciones deseadas. |

Un cero observado significa que no existe evidencia positiva vigente. El detalle
JSON distingue ausencia, error, desconocido, ambigüedad y datos históricos. Los
bits compactos no sustituyen esa información.

## Reglas de combinación

| Combinación | Comportamiento |
| --- | --- |
| Descargar o actualizar, sin destino local | Adquirir en caché; no desplegar. |
| Destino local, sin descargar/actualizar | Usar caché existente; si falta, detener la fase con explicación. |
| RAM y SSD | Dos destinos solicitados; se evalúan por separado. |
| Bastion | Respaldo para balancear descargas; presupuesto igual al SSD, uso independiente. |
| Origen | Mantener procedencia y enlace; no implica transferencia propia. |
| Preservar y actualizar | Conservar el artefacto anterior y adquirir el nuevo con identidad separada. |
| Archivar | Implica preservación efectiva, sin reescribir la política introducida. No activa borrados. |
| Receta existente | Activa su presencia; su prueba de arranque se registra aparte. |
| Candidato PXE | Solicitud de investigación, sin aprobación automática de receta. |
| Resolver | Permite sustituir una referencia dinámica por un artefacto concreto dentro de su regla. |

Niveles C: `0` desactivado; `1` consulta de fuente declarada; `2` versión,
arquitectura, mirror y checksum según adaptador; `3` habilita el alcance profundo
que ofrezca el adaptador. Los límites y hosts de confianza se conservan. La
cobertura efectiva depende de los adaptadores incluidos; no se afirma que todos
los índices y procedimientos de todas las distribuciones estén soportados.

## Catálogo

`schema` es `aux-catalog-v8`; `entries` contiene recursos con `id`, `family`,
`release`, `architecture`, `kind`, `original_url` y `policy`. El ID es estable.
La identidad de artefacto depende de procedencia, versión, arquitectura y hash.
La identidad de prueba incluye además componentes y receta.

`artifact_type` distingue ISO, componente, sistema raíz o manifiesto. Los recursos
chroot declaran `deploy_method` y `procedure_url`. `paths` permite fijar rutas
relativas por destino. Sin ellas, la publicación usa un prefijo de destino,
recurso, versión y pin que conserva copias separadas en RAM y SSD, y archivos
distintos con el mismo nombre. El pin de
los archivos no cambia el identificador de las páginas.

Los checksums oficiales conservan `checksum_source`; una suma local no acredita
la firma del editor. Los metadatos anteriores siguen siendo históricos hasta
resolver y comprobar sus fuentes.

Las recetas utilizan datos estructurados: Linux o menú de proveedor admitido,
firmware, arquitectura, kernel, initrd y argumentos. No se ejecuta shell recibida
como dato de receta. Solo las recetas aprobadas entran en el menú de componentes;
la aprobación no activa S:8.

## Estado

`status.json` utiliza `aux-status-v1`: fecha, huellas del catálogo/configuración,
observaciones por ubicación y máscara por recurso. `generate` exige una
instantánea vigente para el mismo catálogo/configuración.

La prueba usa `aux-boot-evidence-v1`: recurso, identidad, resultado `login-reached`,
fecha, entorno, firmware y hash del log. El log permanece privado. Modificar el
artefacto/receta o perder la evidencia invalida la afirmación para esa combinación.
Los informes públicos no incluyen rutas privadas de logs.

Los 69 perfiles aportados por Ei se incorporan en beta.3 como referencias de origen, sin capability_mask. Sus arquitecturas declaradas, artefactos y procedencia se conservan como metadatos; no se convierten en pruebas de descarga, firma ni login.

## Prioridad P

`priority` es un hexadecimal independiente de `policy` CDE; su defecto es `0`, compatible con catálogos anteriores. Los indicadores se combinan: `5` significa usuario y obligatorio; no es una escala numérica. `priority_sectors` delimita las preferencias de tendencia/IA a Fedora, Debian o Alpine; sin ámbito explícito se usa la afinidad del recurso. P no activa download, deploy, checksum, disponibilidad ni login.

La propuesta ordena primero obligatorio, después usuario, tendencia y sugerencia IA dentro de su sector, y finalmente los criterios técnicos. Obligatorio conserva su selección si excede el presupuesto y muestra el conflicto; no elude los límites de ejecución ni permite bytes sin integridad. Una sugerencia IA no equivale a una receta aprobada. Las preferencias manuales se conservan.

    ./aux catalog set-priority --resource ID --priority 5 --apply
    ./aux catalog set-priority --resource ID --priority A --sector fedora --apply

El dígito anterior R queda sustituido por P. Los A/S de instantáneas importadas no sobrescriben P ni CDE editados. Se conservan los ocho bits observados y se muestran 24 casillas en orden 23…0.

## Catálogo e IA

```bash

./aux catalog preset --preset alpine --preset fedora --apply
./aux catalog set-policy --resource ID --policy E16
./aux catalog set-policy --resource ID --policy E16 --apply
./aux catalog refresh --resource ID --apply
```

Los presets añaden valores sin borrar cambios manuales. Resolver una referencia
dinámica modifica la identidad del artefacto; comprobar de nuevo antes de generar.
Los recursos sin regla única se conservan y se explica el fallo.

Cada guardado genera el sidecar SHA-256 del catálogo. La opción `refresh --commit`
utiliza `catalog_git_repository`, comprueba que el catálogo esté dentro y que Git
tenga identidad configurada, y confirma solo el catálogo y su sidecar. No hace
push ni confirma otros cambios preparados. El temporizador semanal conserva su
calendario; antes de activarlo hay que preparar el repositorio y la configuración
del servicio. Esta entrega no activa el temporizador.

GPT/Gemini permite elegir proveedor, modelo, objetivo y Max tokens. Se revisa la
consulta y se verifican fuentes antes de aceptar. La confirmación final guarda
recursos/políticas en el catálogo; no instala ni acredita pruebas de arranque.

Las descargas usan `jobs` de `fast-boot.json` (1–16); `--jobs N` permite
cambiarlo en una ejecución. Cada parcial mantiene su propia identidad y los
errores de transferencia se notifican antes de terminar la fase.

El asistente de réplica `aux-release` conserva su flujo por fases. Tras verificar
los hashes remotos, genera una instantánea compatible con checkstatus y la
publicación la consume. Una verificación sin fecha o caducada exige repetir
`verify`; regenerar páginas no renueva la fecha de observación remota.

## Inventario de Bastion

En `fast-boot.json`, `checkstatus.bastion` contiene:

| Campo | Uso |
| --- | --- |
| `enabled` | Activar la consulta al servidor configurado. |
| `transport` | `rsync`, `ftps` o `ftp`, según el acceso disponible. |
| `directories` | Pares `path` y `public_url`: directorio remoto y descarga pública. |

FTPS utiliza los campos FTP y el almacén privado. Rsync utiliza los parámetros
SSH de `mirror` y los hosts conocidos de SSH. Hay límites de tiempo, profundidad
y archivos. No hace falta Python en Bastion para listar mediante FTPS o rsync.

Un acceso fallido queda como desconocido/error y conserva la observación positiva
anterior como historia. No se publica como disponibilidad actual. Las rutas
relativas ambiguas requieren separar prefijos o configurar rutas explícitas.

## Descargar, desplegar y generar

La descarga exige SHA-256 fijado, admite parciales con validador HTTP para reanudar
y conserva una copia válida ante un error. Los artefactos distintos se separan.
La descarga y el despliegue requieren sus propios planes y `--apply`.

RAM/disco reutiliza el preparador de ISO. Los componentes se publican por su tipo.
Un stage3 alojado necesita todavía su procedimiento chroot: copiar el archivo no
crea un sistema instalado. La réplica integral sigue en aux-release.

Tras desplegar, ejecutar checkstatus. `generate` consume el inventario y publica
índices, documentación, catálogos y menús; no consulta Bastion durante esa fase.
Los enlaces de Bastion proceden de las URL públicas observadas.

## Prueba hasta login

Arrancar el instalador en el entorno elegido y conservar un log identificable.
Registrar después con `./aux checkstatus --help`. La atestación del operador no
es una interpretación automática del texto del log ni sustituye la prueba real.
Checksum y login son evidencias distintas.

## Instalación, mantenimiento y API

`aux-setup` conserva ISO/base nueva/sistema actual, con el sistema actual al final
y plan confirmado. `aux-enter` conserva inspección, montajes, LVM y chroot;
`aux-observe` conserva osquery/osctrl. Se incluye el contrato anterior
`docs/api/aux-go-openapi-v0.1-draft.yaml` como material de revisión. No se crea un
servidor nuevo de administración ni se modifica el contrato osctrl. Las nuevas
API de mantenimiento/instalación siguen pendientes de definición funcional.

# CDN: primer piloto para AUX

Timestamp: 2026-11-27 | Version: 8.0.1-beta.8  
Author & Credits: https://www.alawise.es/1-s

Inventario y réplica Excalibur/Bastion deben funcionar antes del piloto. La CDN
añade distribución HTTP con caché; no acredita réplica ni pruebas de arranque.

1. Revisar el apartado CDN del alojamiento OVH: oferta incluida/contratada o
   disponible y dominios afectados.
2. Elegir un dominio piloto y unos pocos archivos públicos estáticos versionados,
   por ejemplo estilos e imágenes.
3. Preparar reglas de duración de caché, actualización y purga para esa oferta.
4. Verificar origen/CDN, contenido/hashes y actualización tras publicar una nueva
   versión, conservando una vía de acceso al origen.
5. Evaluar aparte ISO grandes y componentes: tamaño admitido, reanudación,
   solicitudes parciales y cliente iPXE concreto.

El catálogo mutable, menu.ipxe, sesiones, formularios TEC/CLI y API requieren
tratamiento propio; el primer piloto no los incorpora automáticamente a caché.
Este paquete no modifica DNS, contrata opciones ni activa CDN.

Referencia oficial consultada el 22/11/2026:
https://docs.ovhcloud.com/en/guides/web-cloud/web-hosting/cdn-how-to-use-cdn

Los límites deben comprobarse para el servicio concreto; un cupo de precarga no
